# Acceptance Criteria

## MVP
- [ ] AC-001 Managed Windows 11 endpoint launches the dedicated research browser using a valid existing Entra session without a separate password prompt.
- [ ] AC-002 Only protected research-browser traffic uses Azure egress; normal applications retain normal routing. *(Separation evidenced 2026-09-04, ADR-0001 register item 1: a rule bound to the research browser's image path leaves ordinary Edge untouched, while two profiles of one installation cannot be told apart — which is why C2 uses a distinct binary. Driven end to end against the demo harness with that enforcement live, the research browser's only connection was the agent's loopback proxy and it made no other outbound connection at all. The Azure half is AC-003.)*
- [ ] AC-003 External validation sees the selected Azure egress IP rather than the organisation's normal fixed public IP. *(Half evidenced 2026-09-04: the spaincentral node's own egress is **68.221.129.82**, inside the approved NAT prefix `68.221.129.82/31`, against **195.158.108.154** for ordinary egress from the same network — two independent third-party echoes agreeing. **Browser traffic has not yet traversed it.** The node fails closed with no TLS material: `mina-fetch-certs` is a stub pending M2-2d, so it exits non-zero, Envoy's `Requires=` never resolves, nothing listens on 8443 and the load balancer has no healthy backend. Behind that, the on-premises control plane still signs with the development CA (M2-2c remaining, itself waiting on M4-18), so issued session certificates would not chain to the node's trust anchor either. Both halves must land before this can be claimed.)*
- [ ] AC-004 Loss of protected connectivity does not silently fall back to ordinary egress. *(Browser-side evidenced 2026-09-04, ADR-0001 register item 3: with a fixed proxy nothing was listening on — applied as policy, to a second profile, and as a launch flag — direct egress measured zero packets at the NIC against a live baseline and a recovering control. Agent-side fail-closed is separately proven in `tests/integration` (tunnel loss ⇒ HTTP 502, never a direct path). Full evidence needs the live stamp and the managed ring.)*
- [ ] AC-005 DNS leak testing passes. *(Evidenced 2026-09-04, `tests/security/windows-enforcement/Invoke-DnsLeakVerification.ps1`: measured categorically against this machine's actual configured DNS resolvers (decoded packet capture checked for the literal target hostname, not a packet-count threshold — an adversarial review found the first version's threshold could plausibly have waved through a real 2-4-packet leak as background noise; corrected). Chromium's own async resolver bypasses the Windows DNS API entirely, so an ETW-based first attempt at this script read a false "no resolution happened" because of it — also corrected. Verified live, twice: the target hostname is queried unproxied and not queried once proxied, including under the real shipped flag set, with the stand-in proxy independently confirmed to have received the CONNECT for it. **Does not cover N12's other half** — page-triggered DNS prefetch/preconnect (`<link rel="dns-prefetch">`), deferred to the ADR-0007 decision, or the WFP-DNS-block-for-the-binary defence-in-depth layer N12 also names. Full criterion needs the live stamp and a real analyst session, per AC-004's own note.)*
- [ ] AC-006 IPv4/IPv6 leak/fallback testing passes. *(IPv6 half built 2026-09-04, `tests/security/windows-enforcement/Invoke-Ipv6LeakVerification.ps1`, framed against THREAT_MODEL §7's accepted IPv4-only-egress-at-MVP scope: the question is a direct fallback route, not dual-stack support. Measured categorically against the target's own resolved address, not an unscoped IPv6 filter — an adversarial review found the unscoped version could not attribute traffic to the target at all, and its case ladder had never actually executed on this host to be checked. Fixing it surfaced a second, self-caught bug: `pktmon`'s decoded output always echoes a filter's own configured address in a metadata line regardless of whether anything matched it, which made an early attempt at the fix read every case as a leak; corrected by excluding that line before matching, then reconfirmed clean. Run for real against a genuine AAAA-only target and correctly reported **not testable on this host** — no global unicast IPv6 address here, only link-local/ULA, confirmed by the script itself rather than assumed, with the raw per-case data now consistent with that (nothing reached, in any case) rather than a stray false positive. Needs a host with real IPv6 transit to actually exercise the case ladder end to end. IPv4 half not yet separately targeted.)*
- [ ] AC-007 WebRTC/common browser leakage testing passes according to the approved design. *(Evidenced 2026-09-04, ADR-0001 register item 5, `tests/security/windows-enforcement/Invoke-WebRtcLeakVerification.ps1` driving the new `tests/security/canaries/webrtc-harness.html`: **a fixed proxy does not stop WebRTC UDP at all**, while `--webrtc-ip-handling-policy=disable_non_proxied_udp` and the policy `WebRtcLocalhostIpHandling=disable_non_proxied_udp` each suppress it at source, and the image-path block drops it at the network layer if the flag is stripped. What an adversary site learns: a single host candidate, mDNS-obfuscated with no literal address on Edge 153 — the leak is the UDP egress, not the candidate text. QUIC is untouched, and the full criterion needs the M1-6 suite against a live stamp.)*
- [ ] AC-008 Analyst can select an approved EU region and cannot select an unapproved region.
- [ ] AC-009 Default telemetry correlates the approved URL/hostname data with user, device and session. *(Ingest attributes every record to a session — and through it to user and device — or discards it; tested. The correlated data is readable back out only through the M3-8 browsing-data review view (2026-09-23): a separate `Mina.TelemetryViewer` role, every query audited as `telemetry_viewed`, a Sensitive session's id never passed to the hostname query. Full evidence needs the live stamp.)*
- [ ] AC-010 Sensitive URL suppression cannot activate without manager approval.
- [ ] AC-011 Sensitive-session approval automatically expires.
- [ ] AC-012 Sensitive sessions retain mandatory non-URL audit events. *(Suppression is enforced authoritatively at ingest: a suppressed session's destinations are discarded and reduced to counts even if a node sends them, and the discrepancy raises a critical event; tested at service and HTTP level.)*
- [ ] AC-013 Wazuh receives the documented security/audit event set. *(The event set is emitted to a durable, hash-chained audit store and tested; delivery to Wazuh is M3-5. Since ADR-0006 the relay sits on the organisation's network beside Wazuh, so this is a local hop with no tunnel precondition.)*
- [ ] AC-014 SigNoz receives documented operational telemetry without accidental sensitive URL leakage. *(Scrub processors sit on the trace and log pipelines ahead of any exporter, with no way to disable them; content-scan tests assert a destination emitted as a span attribute or interpolated into a log message never reaches the exporter. Delivery to the real SigNoz is M3-6 — a local hop since ADR-0006.)*
- [ ] AC-015 Break-glass is unavailable to ordinary analysts and use generates a high-severity event.
- [ ] AC-016 Egress endpoints are not externally usable as unauthenticated/open proxies. *(mTLS against the internal CA plus node-side session admission since D-19/M4-11 — a chained, unexpired certificate is necessary but no longer sufficient; verified against a real Envoy and the sidecar in Docker: `EnvoyClientAuthTests`, `EnvoySessionAdmissionTests`. **Verified against the deployed dev stamp 2026-09-04** by `tests/security/exposure` (M1-7): no certificate, a foreign CA, cleartext proxy verbs and a port sweep all refused, and a certificate the live Key Vault CA genuinely signed — for a session the control plane has never listed — completed TLS and was then refused `403 Forbidden` by admission. That last case is D-19's "necessary but not sufficient" on real infrastructure rather than in Docker.)*
- [ ] AC-020 A revoked or unknown session cannot open a new tunnel at an egress node beyond one session-view refresh interval, and a node that cannot reach the control plane refuses new tunnels rather than admitting on certificate validity alone. *(D-19/M4-11, `EnvoySessionAdmissionTests` against a real Envoy: revoked-session refusal, unknown-session refusal, and the fail-closed case with no sidecar answering, each with a passing control leg and a meta-test proving the fail-closed assertion would notice `failure_mode_allow` being turned on. Explicitly does **not** cover a tunnel already open at the moment of revocation — accepted limitation, THREAT_MODEL §7 item 6.)*
- [ ] AC-017 Egress nodes cannot reach internal corporate/RFC1918 destinations except explicitly approved platform dependencies. *(Since ADR-0006 the approved set is empty: the control plane is reached at a public endpoint, so the deny is blanket and stays an assertion rather than an allowlist. **No longer only an assertion as of 2026-09-04**: `tests/security/exposure/Invoke-NodeReachabilityProbe.ps1` opens connections from the live node as the `mina-envoy` account — 10/8, 172.16/12, 192.168/16, CGNAT, link-local and loopback all blocked, with two controls proving the deny is specific rather than a dead network: the same account reaches the public internet, and root reaches IMDS. That root/`mina-envoy` split is M4-10's uid-scoped rule, which node provisioning depends on not being host-wide.)*
- [ ] AC-018 A clean test environment can be recreated from source-controlled IaC. *(Both halves: the Azure stamp and support resources, and the on-premises control plane from `environments/dev-onprem` — a hand-built Proxmox plane does not satisfy this.)*
- [ ] AC-019 Security tests are automated where practical and evidence is retained with the release.
